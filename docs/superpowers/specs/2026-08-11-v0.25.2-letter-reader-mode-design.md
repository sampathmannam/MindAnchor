# v0.25.2-B — letter reader-mode (WCAG 2.2 SC 1.4.4)

**Date**: 2026-08-11
**Status**: drafted
**Builds on**: v0.25.2 (the letter inbox + reader; this spec is the size toggle on top)
**Standard**: WCAG 2.2 Success Criterion 1.4.4 (Resize text) — text resizable up to 200% without loss of content or functionality

## Decisions in scope

- Three text sizes for the letter surface (inbox + reader): **Small** (14sp), **Medium** (18sp, default), **Large** (32sp). Large is exactly 200% of the WCAG 1.4.4 reference body (16sp).
- A 3-state `SegmentedButton` or `FilterChip` row in the letter reader header.
- A "Reading size" `SectionHeading` + 3-state control in Settings → Reading, mirrored from the reader, for discoverability.
- Per-user persistence via a new `ReaderPrefs` DataStore (separate from `LetterStore` so the size outlives letter deletion and so future surfaces can reuse it).
- The size applies to the entire letter surface: inbox row previews, the reader title, the reader body, the reader disclaimer footer. It does **not** apply to the navigation chrome (back, delete) — those stay at the platform default so the chrome never grows with the text.
- The "200% without loss of content or functionality" bar: at Large, the letter body wraps correctly inside the safe-drawing area, vertical scroll still works, the back / delete / size controls remain reachable, no horizontal scrollbar appears, no content is clipped.

## Out of scope (deferred)

- **The report screen** ("Last night's look"). The same pattern would apply (the report is also long-form reading), but the user picked "Letter reader-mode" for v0.25.2 specifically. Report reader-mode is a v0.25.3 add — the `ReaderPrefs` class is designed to be reused.
- **System font scale**. The Android system has its own `Settings → Display → Font size`; we deliberately do not bind to it. The user controls both independently — the in-app toggle is for "this surface, today" and the system scale is for the whole phone. Binding them would surprise users who want one and not the other.
- **Per-letter font choice** (serif / sans / mono). Out of scope; reader-mode is about size, not typeface.
- **Per-letter line height / letter spacing**. Out of scope.
- **Multi-language strings** for the size labels. English-only for v0.25.2; copy is "Small" / "Medium" / "Large".

## Why this scope

WCAG 2.2 SC 1.4.4 says text must be resizable up to 200% without loss of content or functionality. The current letter reader renders at `bodyLarge` (16sp) and has no size control. A user with low vision who installs the app and reads the letter either tolerates 16sp or leaves. The audit surfaced this as the highest-value accessibility win for v0.25.2.

The minimum compliant shape is a single 200% toggle. The richer shape (3 sizes) is small additional work and is what the audit recommended, so the spec lands there.

## Architecture

### 1. New `ReaderPrefs` DataStore

**`app/src/main/java/org/mindanchor/reader/ReaderPrefs.kt`** (new file):

```kotlin
data class ReadingSize(val sp: Int) {
    companion object {
        val SMALL  = ReadingSize(14)
        val MEDIUM = ReadingSize(18)  // default; one step above 16sp baseline
        val LARGE  = ReadingSize(32)  // exactly 200% of 16sp baseline (WCAG 1.4.4)
    }
}

class ReaderPrefs(private val context: Context) {
    private val key = intPreferencesKey("reading_size_sp")
    val size: Flow<ReadingSize> = context.readerDataStore.data
        .map { prefs -> prefs[key]?.let(::ReadingSize) ?: ReadingSize.MEDIUM }
    suspend fun setSize(size: ReadingSize) {
        context.readerDataStore.edit { it[key] = size.sp }
    }
    private companion object {
        private val Context.readerDataStore by preferencesDataStore(name = "reader_prefs")
    }
}
```

Notes:
- `ReadingSize` is `data class` so equality is structural and the same size is `==` across recompositions.
- Default is `MEDIUM` (18sp). One step above 16sp baseline because the letter body at 16sp is comfortable for most but slightly tight for sustained reading.
- `LARGE` is exactly 200% of 16sp baseline. WCAG SC 1.4.4 says "up to 200 percent" — `LARGE` is the maximum compliant size.

### 2. `ReaderPrefs.size` flows into the surface

**`LetterScreen` gains a `size: ReadingSize` parameter** (defaults to `ReadingSize.MEDIUM` for tests):

```kotlin
@Composable
fun LetterScreen(
    letters: List<Letter>,
    selectedDate: LocalDate?,
    modelFits: Boolean,
    size: ReadingSize,                           // new
    onSelect: (LocalDate) -> Unit,
    onBack: () -> Unit,
    onDelete: (LocalDate) -> Unit,
    onSetSize: (ReadingSize) -> Unit,            // new
)
```

`HomeScreen` reads the size from a new `viewModel.letterSize: StateFlow<ReadingSize>` and threads it into the `Letter` surface branch.

### 3. Typography

Add a `readerTypography(size: ReadingSize)` helper (private to `LetterScreen.kt`):

```kotlin
private fun readerTypography(size: ReadingSize) = TextStyle(
    fontSize = size.sp.sp,
    lineHeight = (size.sp * 1.45f).sp,   // ~145% line height; matches Material's bodyLarge ratio
    letterSpacing = 0.5.sp,
)
```

Three `Text`s in the reader use this style directly:
- The friendly-date title (style = `headlineMedium.copy(size = size.sp * 1.75f).sp, fontWeight = Light)`) — title scales with the body, just larger.
- The body.
- The disclaimer footer (style = `bodySmall.copy(fontSize = size.sp.sp * 0.85f)`) — disclaimer stays a bit smaller than the body for hierarchy, but still scales.

The `LetterRow` date label and first-line preview also use the scaled size — the inbox scales with the reader so the user picks once and sees it everywhere on the letter surface.

### 4. Toggle UI in the reader header

`LetterReader`'s top row becomes:

```kotlin
Row(
    modifier = Modifier.fillMaxWidth().padding(bottom = Spacing.Tight),
    verticalAlignment = Alignment.CenterVertically,
) {
    TextButton(onClick = onBack) { Text(stringResource(R.string.action_back)) }
    Spacer(Modifier.weight(1f))
    // 3-state segmented control, Material 3 SegmentedButton
    SingleChoiceSegmentedButtonRow {
        listOf(ReadingSize.SMALL, ReadingSize.MEDIUM, ReadingSize.LARGE).forEachIndexed { i, s ->
            SegmentedButton(
                selected = size == s,
                onClick = { onSetSize(s) },
                shape = SegmentedButtonDefaults.itemShape(index = i, count = 3),
            ) {
                Text(
                    when (s) {
                        ReadingSize.SMALL  -> "A-"
                        ReadingSize.MEDIUM -> "A"
                        ReadingSize.LARGE  -> "A+"
                    },
                    style = MaterialTheme.typography.labelLarge,
                )
            }
        }
    }
    Spacer(Modifier.weight(1f))
    IconButton(onClick = { pendingDelete = true }) {
        Icon(Icons.Default.Close, contentDescription = stringResource(R.string.letters_delete))
    }
}
```

Notes:
- `SingleChoiceSegmentedButtonRow` is the Material 3 idiom; it's accessible by default (each button is a 48dp minimum touch target, the active one is announced by TalkBack).
- The labels `A-` / `A` / `A+` are universal enough that they don't need a locale string (and they don't fight RTL).
- The back button and the delete button are pushed to the edges (`Spacer(weight(1f))` on each side) so the segmented control is centred.

### 5. Settings → Reading: "Reading size" sub-section

In the same `SettingsGroup.READING` block, add a "Reading size" `SectionHeading` + 3-state segmented control below the new "Daily letter" sub-section. Same `viewModel.letterSize` flow, same `viewModel::setLetterSize` handler. Lets the user discover the toggle without first opening a letter.

```kotlin
SectionHeading(R.string.reading_size_section, SettingsSection.PULSE, goals)
Text(
    text = stringResource(R.string.reading_size_explainer),
    style = MaterialTheme.typography.bodySmall,
    color = MaterialTheme.colorScheme.onSurfaceVariant,
)
val letterSize by viewModel.letterSize.collectAsState()
SingleChoiceSegmentedButtonRow(modifier = Modifier.padding(top = 8.dp)) {
    listOf(ReadingSize.SMALL, ReadingSize.MEDIUM, ReadingSize.LARGE).forEachIndexed { i, s ->
        SegmentedButton(
            selected = letterSize == s,
            onClick = { viewModel.setLetterSize(s) },
            shape = SegmentedButtonDefaults.itemShape(index = i, count = 3),
        ) { Text(when (s) { ReadingSize.SMALL -> "A-"; ReadingSize.MEDIUM -> "A"; ReadingSize.LARGE -> "A+" }) }
    }
}
```

### 6. WCAG layout safety at Large

`LARGE` (32sp) is the worst case. To honour SC 1.4.4 ("without loss of content or functionality"):

- The reader `Column` is `verticalScroll(rememberScrollState())` — already there from spec 1.
- The body `Text` has no `maxLines` cap and no `softWrap = false` — it wraps and the column scrolls.
- The body's `Modifier.fillMaxWidth()` (already there) — no horizontal overflow.
- The date title at `size.sp * 1.75f` (56sp at Large) wraps to 2 lines if needed; the title has no `maxLines` cap.
- The disclaimer at `size.sp * 0.85f` (27sp at Large) — no maxLines cap, wraps if needed.
- The header row is `padding(bottom = Spacing.Tight)` and `fillMaxWidth()` — the segmented control stays inline even at Large because `A-` / `A` / `A+` are short.
- The back button and delete `IconButton` are 48dp regardless of size — they don't grow with the text.
- Vertical scroll must reach the disclaimer footer; the back / delete / size controls are inside the scroll (top) — they stay visible because the user can scroll up. This is the same shape as the existing report.

A finding test (`LetterLargeSizeLayoutFindingTest`) renders `LetterReader` at `LARGE` with a 4000-character body and asserts:
- `body.lineCount > 1` (it wraps)
- `column.verticalScrollState.maxValue > 0f` (it scrolls)
- `backButton.bounds.intersects(root.bounds)` (back is reachable)
- `deleteButton.bounds.intersects(root.bounds)` (delete is reachable)
- `sizeControl.bounds.intersects(root.bounds)` (size is reachable)

### 7. What does NOT change

- The chrome (back, delete, size) uses platform-default sizes — they don't scale with the toggle.
- The friendly-date group headers in the inbox ("Today" / "Yesterday" / "Monday" / "Earlier") stay at `titleSmall` regardless of size — they're navigational, not reading content. (Alternative considered: scale with the toggle. Rejected because it makes the inbox feel inconsistent; a 32sp "Today" is louder than the date labels it groups.)
- The corner shortcut ("letters") stays at platform default — it's part of the home chrome.

## Finding tests (the regression net)

1. `ReadingSizeDefaultsFindingTest` (5 tests) — `ReadingSize.SMALL.sp == 14`; `MEDIUM.sp == 18`; `LARGE.sp == 32`; `LARGE.sp == 200% of 16`; the three sizes are pairwise distinct.
2. `ReaderPrefsRoundTripFindingTest` (5 tests) — default is MEDIUM; `setSize(SMALL)` followed by read returns SMALL; `setSize(LARGE)` followed by read returns LARGE; `setSize(MEDIUM)` followed by read returns MEDIUM; re-instantiating `ReaderPrefs` returns the last set value (DataStore persistence).
3. `LetterReaderTypographyFindingTest` (5 tests) — at SMALL, body `fontSize` is 14sp; at MEDIUM, 18sp; at LARGE, 32sp; `lineHeight` is 145% of `fontSize` at all three sizes; the disclaimer `fontSize` is 85% of body `fontSize` at all three sizes.
4. `LetterLargeSizeLayoutFindingTest` (5 tests) — the 4000-char body wraps to > 1 line at LARGE; the column's `verticalScrollState.maxValue > 0f` at LARGE; the back button's bounds intersect the root at LARGE; the delete button's bounds intersect the root at LARGE; the size control's bounds intersect the root at LARGE.
5. `LetterReaderSizeToggleFindingTest` (5 tests) — `SingleChoiceSegmentedButtonRow` is used (not three separate buttons); tapping a different segment calls `onSetSize` with the right value; the currently-selected segment is `selected = true`; each segment is a 48dp minimum touch target; the segmented control is inside the scrollable `Column` (top, so the user can scroll up to reach it after the body).
6. `LetterInboxPreviewScalesFindingTest` (5 tests) — at SMALL, the row preview `fontSize` is 14sp; at MEDIUM, 18sp; at LARGE, 32sp; the row height is `>= 48.dp` at all three sizes (touch target); the date label stays at `titleSmall` regardless of size (it groups, not reads).
7. `SettingsReadingSizeFindingTest` (5 tests) — the "Reading size" section uses `SingleChoiceSegmentedButtonRow`; the control's selected segment matches `viewModel.letterSize`; tapping a different segment calls `viewModel.setLetterSize(s)`; the section heading uses `reading_size_section`; the explainer string is `bodySmall` with `onSurfaceVariant` color.

## Acceptance

- A user with low vision installs v0.25.2-B, opens any letter, taps "A+" in the reader header, and the text grows to 32sp. They can scroll the letter top-to-bottom, hit Back to return to the inbox, hit × to delete the letter, and tap "A" or "A-" to shrink back. The size choice persists across letter opens and across the inbox/reader navigation.
- The same user opens Settings → Reading and finds the same "A- / A / A+" control under "Reading size", confirms the change is reflected, and changes it there too — both controls are in sync because they share the `ReaderPrefs` DataStore.
- At "A+", no horizontal scrollbar appears in the letter body. The back button and the delete button are still visible at the top of the scroll. The "Today" / "Yesterday" / "Monday" / "Earlier" group headers in the inbox are still at `titleSmall` (they are navigational, not reading content).
- The system font scale (`Settings → Display → Font size`) is independent of the in-app toggle. A user with both at max is at ~250% effective; the in-app chrome uses platform defaults and the letter body uses the in-app size.
- The senior-tester audit (v0.25.2) includes a reading-size walkthrough and finds no P0/P1 bugs.
- No new outbound network calls; no new permissions. The `NetworkCallsForbiddenTest` still passes.

## Acceptance string

- A new user installs v0.25.2-B, opens the latest letter, taps "A+" in the reader header, and reads the letter at 32sp. They switch to "A-" and the text shrinks to 14sp. They switch back to "A" (the default) and continue reading. They close the app, reopen it, and the letter is still at "A". They open Settings → Reading, see the same "A- / A / A+" control, and confirm the same value.

## Why this spec is one of two, not three

- The audit's "letter reader-mode" recommendation has two pieces: (1) build the reader surface, (2) add the size toggle. Spec 1 is (1); this spec is (2). They ship in the same v0.25.2 because the spec 1 reader renders at the platform default until this spec lands; if a user installs v0.25.2 and reads a letter before v0.25.2-B ships, the experience is the existing 16sp. That's fine; the toggle is incremental.
