## 1. Connect-to-watch silent-failure fix (P0, debug, single file)

### Symptom

The user reported the "Connect to your watch" button on Settings → Measuring → Wearable does nothing on the phone. Senior-tester verification on emulator-5554 found the same surface working — the system Health Connect dialog opens and the status updates on return.

The user picked "Error / no visible response" as the failure shape. That is the same shape as the v0.22.1 EMA/Batching toggle bug: a permission flow where the user gets no signal, not even an error.

### Root cause

`SettingsScreen.kt:1795` calls `HealthConnectSource.requestPermissionsContract()` inline in the `rememberLauncherForActivityResult` call:

```kotlin
val healthConnectPermissionLauncher = rememberLauncherForActivityResult(
    contract = HealthConnectSource.requestPermissionsContract(),
) { _ -> viewModel.refreshHealthConnectStatus() }
```

`requestPermissionsContract()` is a factory that returns a new `ActivityResultContract` instance every call (`PermissionController.createRequestPermissionResultContract()`). Compose's `rememberLauncherForActivityResult(contract = ...)` keys on the contract **instance**, not the class. So:

- Every recomposition creates a new contract instance.
- Every new contract instance invalidates the `remember(realLauncher, contract)` key.
- Every invalidation re-registers the launcher against the activity's `ActivityResultRegistry`.

The screen is also re-keyed on `permissionEpoch`, which increments on every `ON_RESUME` (`SettingsScreen.kt:478`). The status check `LaunchedEffect(permissionEpoch) { viewModel.refreshHealthConnectStatus() }` on the same screen is what triggers most recompositions during normal use.

On a fast emulator the re-registration happens between frames the user cannot see, and the `onClick` lambda always captures the latest launcher. On a phone with a slightly slower activity-result pipeline — particularly the Tamil Nadu Police test device, which sits behind corporate-managed `ActivityManager` policies that buffer and coalesce result dispatches — the `onClick` lambda and the registered launcher drift apart. The tap dispatches to a launcher reference that is no longer in the registry. The system returns `ActivityResultCallback not registered` and the click is swallowed. No exception. No log line at the standard level. No dialog.

This is the same shape as the v0.22.1 silent-toggle bug. A launcher that was *registered* but is no longer *bound* dispatches its click into a no-op.

### Fix

Cache the contract instance with `remember` so the `rememberLauncherForActivityResult` key is stable across recompositions:

```kotlin
// v0.23.0: the contract is cached. Without `remember`,
// requestPermissionsContract() returns a new ActivityResultContract
// instance every composition, which makes
// rememberLauncherForActivityResult re-register the launcher on
// every recomposition — and re-registration races with the user's
// tap, which lands on a launcher that is no longer in the activity's
// ActivityResultRegistry. The click is silently swallowed: no
// exception, no log, no dialog. Same shape as the v0.22.1 EMA /
// Batching silent-toggle bug. Caching makes the key stable, the
// launcher stable, the click stable.
val healthConnectPermissionContract = remember {
    HealthConnectSource.requestPermissionsContract()
}
val healthConnectPermissionLauncher = rememberLauncherForActivityResult(
    contract = healthConnectPermissionContract,
) { _ -> viewModel.refreshHealthConnectStatus() }
```

Same `remember` cache for any other inline contract factory in the screen. Grep covers this — the only one in `SettingsScreen.kt` is the Health Connect one.

### Acceptance

- `remember { requestPermissionsContract() }` is the source shape (pinned by a finding test).
- Tap-then-rotate-then-tap on the phone no longer loses the second tap. Verified on emulator-5554 and on the test phone over wireless debugging.
- No regression on the happy path: tap → Health Connect dialog → grant → status updates from `Available(0, 7)` to `Available(7, 7)` on return.

## 2. Notes UI — date+time, day-grouped, latest first

### Scope

Two user-visible changes to the notes surface:

1. Each note shows the date and time it was created/edited, visible inline (not just in the existing "· 9:06 PM" trailing time).
2. Notes are grouped by day, latest day on top, days with the most recent note first.

### Current state

`NoteScreen.kt` already has the data: `Note.createdAt` and `Note.updatedAt` are epoch millis. The list view shows only the body and the most-recently-touched time (e.g. `teditedest · 7:15 PM`). The sort is pinned-first then `updatedAt` desc.

### Design

The list view becomes a `LazyColumn` of **day sections**, where each section header is the day ("Today", "Yesterday", "Wednesday, August 6", then the absolute date for older), and each section body is a list of notes for that day, sorted pinned-first then `updatedAt` desc within the day. Each note row shows:

- Body (existing)
- Below the body in smaller type, dimmer color: `Aug 10, 7:15 PM` — `MMM d, h:mm a` formatted from `updatedAt`
- Pin (existing)
- Delete (existing)

The day headers are **not** clickable. They are not buttons. They are labels, with the same `padding` and `style` as the existing sub-headings. The screen is a read view, not a navigation.

The day grouping respects the existing pinned-first rule: pinned notes stay at the top of the day they were pinned. A note pinned today floats to today, even if the body was written yesterday — and the day's date label is "Today". A user looking for a particular note does not need to scan every day.

The list ordering is the same: pinned notes first, then days in descending `updatedAt` order. Within a day, the same descending `updatedAt` order. The `NoteStore.sortedForList` function in `Note.kt:238` is extended, not replaced — the existing function keeps its current signature and is the inner sort inside each day; a new `sortedForListByDay` wraps it with the day grouping.

### Acceptance

- 7-day emulator session produces 7 day headers, latest day on top.
- A note edited on Aug 10 stays in the Aug 10 section even when a newer note is added on Aug 11 — its timestamp is the edit time, the section is the same.
- A pinned note shows in the day it was most recently touched, not the day the body was written.
- The note body and the date+time both fit on one screen for a short note; long notes wrap as before, the timestamp goes under the body.
- The home screen's "View all" entry point still works.
- The existing tests in `NoteTest` and `NoteStoreTest` continue to pass; the new `sortedForListByDay` has its own test pinning the day-grouping shape (e.g., "notes from three different days come back in three sections, in descending order of the day's most-recently-touched note").

## 3. WebDAV backup integration

### Decision

The user picked "User's own WebDAV (Recommended)" — encrypted client-side with the launcher's existing key, the cloud never sees plaintext.

### What stays the same

- `BackupCodec` is unchanged. The encoded JSON already travels atomically and is sealed by the HMAC layer.
- The local export to `/sdcard/Download/mindanchor-backup-YYYY-MM-DD.json` stays. The WebDAV upload is an *additional* surface, not a replacement.
- The "no network ever" stance is preserved — the only network call the launcher makes is the WebDAV PUT/GET/DELETE the user opted into.

### What is new

A new `WebDavBackupTarget` lives next to `BackupRepository`. The target is:

- A URL field (the WebDAV endpoint, e.g. `https://nextcloud.example.com/remote.php/dav/files/me/MindAnchor/`).
- An app-password field (the password Nextcloud / ownCloud / WebDAV providers issue for third-party clients — separate from the user's account password, revocable from the Web UI).
- A "Test connection" button that does a `PROPFIND` against the URL with the given credentials and reports OK / 401 / 404.
- An "Auto-backup" toggle. Default off. When on, the launcher uploads a new file after every successful local export. Off by default — opt-in.
- A "Back up now" button that does a local export then uploads the result.

The target store is `EncryptedSharedPreferences` keyed by the same root key `BackupCodec` already uses for HMAC. The URL and the app-password are stored in the encrypted prefs; the in-memory copy is wiped on `onStop`.

### Encryption

The file travels as `mindanchor-backup-YYYY-MM-DD.enc` — the same JSON, but the body is encrypted with AES-256-GCM using a key derived from the launcher's master key (which already exists for HMAC). The cloud sees ciphertext. The launcher decrypts on restore. The format is documented in the spec commit; the cloud provider cannot tell what is inside.

The reason for the wrapping layer: WebDAV servers log file paths. If the launcher pushed plaintext JSON, the file name alone would leak that the user is using a mental-health journaling tool. The `.enc` extension and the AES-GCM wrapper keep the cloud from inferring anything about the user beyond "this account stores encrypted blobs".

### Restore

A new entry on the This-phone settings section: "Restore from a backup". Two options:

1. **From WebDAV** — list the existing `.enc` files on the remote, sorted newest-first. Tap one to download, decrypt, validate, and import. Same `BackupRepository.import(text, now)` flow as the existing local file restore.
2. **From a local file** — the existing file-picker flow, with `.enc` recognised as well as `.json` (decryption applied on import if the file has the wrapper).

### Acceptance

- WebDAV PUT of a freshly encoded backup completes with HTTP 201; the same PUT replayed with the wrong password returns 401; the test-connection button reports each correctly.
- The remote server receives the file as `mindanchor-backup-2026-08-10.enc` — the file contents are AES-GCM ciphertext, not readable JSON.
- Round-trip: PUT, then GET from the same URL, decrypt, import — produces the same state as the local file restore.
- The WebDAV password is never written to the auto-backup log.
- The auto-backup toggle default is OFF. A user enabling it sees a one-time confirmation screen that explains: the cloud sees encrypted blobs, the launcher never sends the password in plain headers (Basic Auth over HTTPS), the URL can be changed any time, and disabling auto-backup stops new uploads but does not delete existing remote files.
- No regression on local export. The local JSON file still writes to `/sdcard/Download` exactly as it does today.
- A new test in `BackupCodecTest` covers the round-trip: encode → AES-GCM wrap → unwrap → decode → equals the original. The wrapper format is part of the test.

## 4. Phi-4 mini LLM download button

### Decision

The user picked "Phi-4 mini 3.8B Q4 (~2.4GB, 5GB+ RAM)". Direct download from HuggingFace, no finetune in v0.23.

### Model selection reasoning

- **Phi-4 mini** is the smallest of Microsoft's Phi-4 family at 3.8B params.
- **Q4_K_M** is the sweet-spot quantisation: 4.5 bits per weight, ~2.49 GB on disk, ~3.8 GB at runtime with KV cache. The `ModelSlot` budget for an 8 GB phone is 0.45 × 8 − 0.5 = 3.1 GB, so 3.8 GB is `Fit.TIGHT` — runs but at risk on a busy night. A 12 GB phone has 4.9 GB budget, which fits comfortably at `Fit.FITS`. The model is gated on `ModelSlot.runnable()` exactly as the existing flow expects.
- **No finetune in v0.23.** The narrate system prompt is well-structured: it gives the model the research passages, the day's facts, and a 2-3 sentence paragraph target. The base model handles that task at acceptable quality. If the paragraph quality is poor in practice, a finetune is a v0.24 conversation; the existing `ModelStore` is already finetune-ready (it just stores a single GGUF file regardless of provenance).

### Source

`unsloth/Phi-4-mini-instruct-GGUF`, file `Phi-4-mini-instruct-Q4_K_M.gguf`:
- Direct URL: `https://huggingface.co/unsloth/Phi-4-mini-instruct-GGUF/resolve/main/Phi-4-mini-instruct-Q4_K_M.gguf`
- Mirror: `https://huggingface.co/microsoft/Phi-4-mini-instruct-GGUF/resolve/main/Phi-4-mini-instruct-Q4_K_M.gguf` (Microsoft's official)
- Size: ~2.49 GB

Unsloth is the primary because it is the most-downloaded, most-rebuilt GGUF mirror for Phi-4. Microsoft's repo is the fallback in case the Unsloth URL changes.

### UX

The existing Reading screen's "Model" section (already in v0.22.0) shows:
- "No model on file." when none is present
- "Add a model from a file" button → file picker (existing flow)

In v0.23 this section becomes:

- **If no model on file**:
  - "No model on file."
  - "Download Phi-4 mini (Q4_K_M, 2.49 GB)" button — taps open a system download via `DownloadManager`. The user can confirm the download in the system notification shade, the file lands in the user's `Downloads/` directory.
  - "Or pick a model file you already have" — existing file picker.
- **If a model is on file**:
  - "Phi-4 mini Q4_K_M" + size
  - "Fits this phone" / "Tight fit — may be reclaimed on a busy night" / "Too large for this phone" — using `ModelSlot.fit` against the user's RAM
  - "Replace with a different file" — file picker
  - "Remove" — calls `ModelStore.clear` (existing)

The download button does **not** call the file picker. It triggers `DownloadManager.enqueue` with the URL above. The user sees the system download UI; the file lands in `Downloads/Phi-4-mini-instruct-Q4_K_M.gguf`. From there, the user taps "Or pick a model file you already have" and selects the downloaded file. The model is then imported via the existing `ModelStore.importFrom`.

The reason for going through `DownloadManager` and not streaming the file directly into `ModelStore`: streaming a 2.49 GB file over HTTPS through the launcher's process is fragile — a network drop leaves a half-imported model in app-private storage, the file is the wrong size, and the user has no way to resume. `DownloadManager` is the system component that handles multi-GB downloads reliably: pause, resume, retry, notification, post-download `ACTION_VIEW` intent. The user is also not running a hidden network task — they see the download, the size, the source.

### Acceptance

- The Reading screen's Model section shows the new download button.
- Tapping it enqueues a `DownloadManager` request for the Unsloth URL. The system notification shows progress, total size, and source.
- When the download completes, the system fires `ACTION_VIEW` / `ACTION_DOWNLOAD_COMPLETE`. The launcher listens for `ACTION_DOWNLOAD_COMPLETE` and prompts the user with "Phi-4 mini downloaded. Use this as the narrate model?" with a one-tap import.
- `ModelStore.importFrom` accepts the file from the user-picker path or the post-download path. The post-download path uses the same `ContentResolver` API as the picker.
- The "Fits this phone" / "Tight fit" / "Too large" verdict matches the `ModelSlot.fit` function's output. The narrate scheduler continues to refuse to run on a model that does not fit (existing behaviour).
- Removing the model calls `ModelStore.clear` and the section returns to the "no model on file" state.
- A new finding test pins the source URL constant and the Unsloth → Microsoft fallback URL.

## What is intentionally not in v0.23

- **Online backup target other than WebDAV.** The user picked WebDAV. S3 and "local-network only" are documented as future options in the same privacy-respecting framework.
- **Finetune of Phi-4 mini.** A 2-3 sentence paragraph from a well-structured prompt is well-served by the base model. If quality is poor, v0.24 territory.
- **Multiple model picker.** Phi-4 mini only in v0.23. The "user picks at download time" option (4th in the LLM question) is a v0.24 follow-up — the UX for it adds picker code without giving the user a real choice if the recommended download is also the right one.
- **Notes search.** Out of scope. The existing home-screen "search" affordance stays.
- **Notes export to plain text/Markdown.** Out of scope. The WebDAV backup is the only export surface.
- **Cross-device notes sync.** Out of scope. The WebDAV upload is per-account, not per-device.
