# v0.25.0 — auto-classify notes with the on-device LLM

**Date**: 2026-08-11
**Status**: approved
**Includes**: v0.24.0 Item 1 (ASH-style daily letter) — items 2-4 deferred
**Decisions in scope**: 4-type classification of notes, on-device via the v0.23.0 Phi-4 mini, cached on the note, surfaced as a chip on the row, filterable in the list view
**Out of scope**: tasks/reminders as separate inboxes, journaling mood, semantic search, cross-note synthesis, voice journaling, server-side LLM

This is a v0.23.0/v0.24.0 follow-up. The LLM (Phi-4 mini) and the note surface (a free-text, sealed, day-grouped list) are already in place. v0.25.0 makes the LLM read the note and assign a type, and surfaces the type in the UI.

---

## The four key decisions

| # | Decision | Choice |
|---|----------|--------|
| 1 | What the LLM does with notes | **Auto-classify each note** into one of 4 types |
| 2 | Type taxonomy | **4 types, one per note**: `general / task / reminder / journal` |
| 3 | When + where classification runs | **Background after save, stored on the note** as `Note.type: NoteType?` |
| 4 | UI | **Row chip + filter chips above the list** (All / General / Tasks / Reminders / Journal) |

All four are "the smallest change that gives the user what they asked for." The user explicitly named the four types in the brainstorm; the LLM-into-chip path matches every reference app (Reflect, Mem, Notion AI) at its most useful level — without their data-mixing, cloud, or streak drawbacks.

## The remaining calls

| # | Decision | Choice |
|---|----------|--------|
| 5 | Confidence / malformed output | Anything other than the 4 valid types → treat as `general`. No "probably" UI. |
| 6 | Fallback when Phi-4 isn't on the phone | `type = null`, no chip, no "Classify" button. Users without the model see no change. |
| 7 | Re-classify on body edit | Yes. Edits can change the type. One extra LLM call per edit. |
| 8 | Sealing | Type is part of the sealed payload (same HMAC layer as the rest of the note). Backed up with WebDAV. |
| 9 | Backwards compat | Existing notes (v0.23.0 and earlier) have `type = null`. One-time background pass after upgrade. |
| 10 | Stale types | "Re-classify all notes" button in Settings (off by default). |
| 11 | "Classifying…" UI | Subtle shimmer for the ~10s window after save while the model runs. |
| 12 | Chip labels | Full words ("Task", "Reminder", "Journal", "General"). Colors from the existing palette. |
| 13 | Downstream consumers | Letter + night report read typed notes (filter-aware summary). Reflection card + worry feature unaffected. |

## Research

The user asked for research before designing. Findings from the brainstorming pass:

- **Reflect** (cloud, E2E-encrypted): action item extraction, cross-note synthesis, GPT-4. Their "Action items" feature is essentially "extract tasks from free-form text and surface as a list" — the *opposite* of what we picked (we keep the note and *tag* it, no separate store).
- **Mem** (cloud): auto-tagging, AI-native organization, suggested links between notes. Their model is closest to ours — each note gets a tag, the list view filters.
- **Notion AI** (cloud): Q&A across workspace, action item extraction. Their action item extraction is a separate surface, again the opposite of ours.
- **Reor** (local, Ollama): every note chunked + embedded, related notes auto-linked via vector similarity, RAG-style Q&A. The local-first equivalent of Reflect's synthesis. Heavier than what we need right now.
- **Obsidian + Copilot / Smart Connections** (local): local embeddings for semantic search. The on-device "find a note" story. We don't ship search yet, but `Note.type` makes a future "show me all tasks" search trivial.

The interesting mapping: **Mem's auto-tag pattern fits MindAnchor's voice**. We don't need a second store; the note *is* the source of truth, and the type is a label. The LLM's job is to assign a label, not extract or restructure.

## Data model

### `NoteType` enum

```kotlin
package org.mindanchor.model

/**
 * The kind of note a [Note] is. Set by the on-device
 * classifier (v0.25.0) on save; edited notes are
 * re-classified. The launcher is type-less by design;
 * the type is a *label*, not a separate field the user
 * has to fill in.
 */
enum class NoteType {
    /** Catch-all: anything that isn't a task, reminder, or journal entry. */
    GENERAL,
    /** "I need to do this." Verbs, intent, no time. */
    TASK,
    /** "Don't let me forget X." Time-bound, date-anchored, or "tomorrow/next week". */
    REMINDER,
    /** "What happened today / how I felt." First-person, reflective. */
    JOURNAL,
}
```

### `Note` extended

```kotlin
data class Note(
    val id: Long = 0L,
    val body: String = "",
    val createdAt: Long = 0L,
    val updatedAt: Long = 0L,
    val pinned: Boolean = false,
    /**
     * The on-device classifier's read of this note.
     * Null when the model isn't on the phone, or the
     * note was saved before v0.25.0 and the one-time
     * background pass hasn't reached it yet.
     */
    val type: NoteType? = null,
)
```

The new field is on the data class, sealed by the existing `SealedCodecs` layer (the `codecId "notes"` HMAC). The wire format gains one tab-separated token: `id\tpinned\tcreatedAt\tupdatedAt\ttype\tencoded(body)`. `type` is the enum name (`"GENERAL"` / `"TASK"` / etc.) or empty for null. The decoder rejects unknown values as "this line is corrupt, skip it" — the same fail-closed pattern as the rest of the codec.

## Classification flow

### Save

```
User taps "Save" in NoteScreen
  ↓
NoteActivity.onAdd(note)
  ↓
NotesPrefs.add(note)  ← writes the note, type = null
  ↓ (returns immediately to the user)
NoteClassifier.enqueue(note)  ← fire-and-forget
  ↓
LlamaNarrator generates the type
  ↓
NoteClassifier writes back via NotesPrefs.setType(note.id, type)
  ↓
NotesScreen recomposes; the chip appears
```

The "fire-and-forget" is a `CoroutineScope(SupervisorJob() + Dispatchers.IO)` launched from `NoteActivity`, mirroring the existing `appScope` pattern. A failure (model not loaded, OOM, malformed output) is caught and the note stays `type = null`. The list view never blocks.

### Edit

Same flow: `NotesPrefs.edit(id, body, ts)` triggers a `NoteClassifier.enqueue(note)`. The new body is classified; the chip updates. Cost: one LLM call per edit.

### On upgrade (one-time pass)

When the app starts on a build that includes v0.25.0 for the first time:
1. A `SharedPreferences` flag `notes_v0_25_classify_pass_done` is read.
2. If false, every note with `type = null` is enqueued for classification.
3. When the queue drains, the flag is set to true.

The pass is bounded: a device with 1000 untyped notes will see 1000 LLM calls over many minutes. The same `appScope` is reused; the model is already loaded from any prior save.

### "Re-classify all" (manual)

Settings → Daily habits → "Re-classify all notes" → confirm. Resets every note's type to null and re-enqueues. Useful when the user upgrades the model or wants a clean re-read.

## Classifier

A new file `app/src/main/java/org/mindanchor/note/NoteClassifier.kt`. Reuses the same `LlamaEngine.nativeGenerate` as `LlamaNarrator` and `LetterWriter`. The system prompt is a single line: *"You are a one-word classifier. Output exactly one of: GENERAL TASK REMINDER JOURNAL."* The user prompt is the note body. The output is parsed:

- If the output is one of the four enum names (case-insensitive, with optional leading/trailing whitespace) → that type.
- Otherwise → `GENERAL` (the safe default).

`NoteClassifier` is a thin object. There is no `NarrationGuard` — the output is a single token, not a paragraph. There is no `Prompting` (it's a one-line prompt). The seed is derived from the body for reproducibility (same body, same type across attempts).

## UI

### `NoteScreen` changes

- Each row in the day-grouped LazyColumn shows a small colored chip next to the title: `TASK`, `REMINDER`, `JOURNAL`, `GENERAL`. The chip is a `SuggestionChip` (Material 3) sized small. The color is per-type: blue (task), orange (reminder), purple (journal), neutral (general).
- An untyped note (`type = null` or `type` is being computed) shows no chip, with a subtle 10s shimmer placeholder while the model runs.
- Above the LazyColumn, a `Row` of `FilterChip`s: `All` / `General` / `Tasks` / `Reminders` / `Journal`. Tapping one filters; tapping the active one clears (back to All). "All" is the default.

### Filter behaviour

- The filter is in-memory over the loaded `NotesState`. No persistence — the filter resets to "All" on activity open, same as the existing search input.
- Pinned notes stay at the top regardless of filter.
- The day grouping is preserved.
- If the filter is "Tasks" and there are 0 typed tasks, the list shows an empty state: "No tasks yet." (one string).

### "Classifying…" shimmer

A `LinearProgressIndicator` of width 32dp next to the row, animated for the first ~10s after save, then removed. No text — the user already knows they just saved.

## Downstream consumers

### Letter (`WeekDataCollector.collectNotesSummary`)

Replaces the "count + 60-char preview" line with a typed summary:

```
6 notes this week: 2 tasks, 1 reminder, 3 journal. 
Most recent: "I keep putting off the meeting notes."
```

The new line is built by `NoteType` counts over the past 7 days. If there are no typed notes yet (model not on phone, or first week after upgrade), falls back to the old "count + preview" line.

### Night report (`ReportComposer`)

No change to the night report itself. The night report reads the day's events, not the user's notes. Notes are a letter-only signal.

### Reflection card, worry feature

Unchanged. Both are separate surfaces (v0.24.0 Items 3 and 4). The note type doesn't bridge into them.

## Why this release and not the next

- The LLM is already in the user's hand (v0.23.0). It already reads the night report. Reading the note is the same shape, the same engine, the same safety filter — only the prompt and the output format change.
- The note surface is already in the user's hand (v0.20.1 round 5). A small `Note.type` field is a one-line edit to the data class; the seal round-trips because the existing codec is line-based and one extra tab-separated token is the same shape.
- The user asked for it. The brainstorm chose the smallest version (auto-classify, 4 types, cached, chip + filter). The next step is the v0.24.0 letter, which is already implemented and committed in this release; v0.24.0 Items 2-4 (sunlight, reflection, worry) are deferred to a follow-up.
- The risk of "too much" is real: a "tasks inbox" is a separate surface the user didn't ask for, semantic search is a future RAG story, and "all of the above" is a v0.27.0 problem. v0.25.0 is the smallest change that makes notes *better* — better because the user can see what each note is for, and the LLM can read the user's own words back to them.
