## Scope

### WP-A: BackupCodec.kt KDoc update (1 task)

The `BackupCodec.kt` top-of-file KDoc has a contradiction with the shipped v0.23.0 implementation. Update it to:

- **Drop the "refused outright" stance.** Cloud backup is *opt-in* via the WebDAV bridge shipped in v0.23.0 (`org.mindanchor.backup.WebDavBackupTarget`).
- **Keep the "by the person, to a location they pick" framing for the LOCAL save path.** The system file picker is still the primary save destination; no upload happens automatically.
- **Add a "## Outbound channels" section** that distinguishes:
  - **Local** (file picker, no permission, no network call) — the default save path
  - **WebDAV (opt-in, off by default)** — `org.mindanchor.backup.WebDavBackupTarget`, AES-256-GCM wrapped, the user's own bucket (Nextcloud, ownCloud, anything WebDAV-capable), HTTPS-only, no third-party dependency. The cloud sees an encrypted blob; never the plaintext.

This is a KDoc-only change. No code, no tests (the implementation is unchanged and already tested by `WebDavBackupTargetTest`, `EncryptedBackupCodecTest`, and `WebDavBackupFindingTest`).

### WP-B: Watch connect robust failure handling (gated on `adb logcat`)

The user reported "Error / exception / no response" when tapping the "Connect to your watch" button on their physical device. The system Health Connect dialog opens on the emulator but doesn't on the device. The current code:

- `app/src/main/java/org/mindanchor/vitals/HealthConnectSource.kt:131-133` — `isAvailable(context)` returns `false` if `getSdkStatus` returns anything other than `SDK_AVAILABLE`. On a device where HC is technically present but in a bad state, this returns `false` and the button is hidden. But the user says the button was visible and they tapped it.
- `app/src/main/java/org/mindanchor/settings/SettingsScreen.kt:1858-1871` — the launcher caches the contract in `remember` (a v0.23.0 fix), launches with `effectivePermissions(context)`, and the result handler just calls `viewModel.refreshHealthConnectStatus()`.

The fix needs to:
1. **Wrap the launch in try-catch + `runCatching`** — surface `ActivityNotFoundException` if the system can't find an activity to handle the permission intent.
2. **Add `Log.w(TAG, ...)` tracing** around the launch path so the user can capture the failure with `adb logcat` and we have something to root-cause from.
3. **Make the failure visible** — show a Snackbar / Text / explicit error state when the launch fails or returns no granted permissions after an "open" gesture.

The exact code shape depends on the logcat. This WP is **gated on the user providing an `adb logcat` from the failing device**. Without the logcat, we can't distinguish between:
- A `SecurityException` from the launch (no permission)
- An `ActivityNotFoundException` (no system activity handles the intent — common on custom ROMs)
- A silent dismissal (the activity opens and immediately closes)
- A timeout (the system never returns)

Once the logcat is available, this WP gets a 2-3 task plan: read the log, identify the failure mode, fix the silent path. For now, the WP holds a "needs logcat to proceed" gate.
