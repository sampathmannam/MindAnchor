## WP-A: Worry postponement (Borkovec 1994 + Watkins 2008)

**Why**: The current OpenLoop is a fixed "morning return" — the user has no agency over WHEN the worry comes back. Borkovec's worry-postponement protocol says the user should be able to schedule a SPECIFIC time to revisit a worry, and that *the act of scheduling* is the active ingredient. Watkins 2008 meta-analysis: scheduled worry is more effective than suppression.

**Change**:
- `LoopPhase` gains `POSTPONED` (the worry is parked until a user-chosen timestamp).
- `OpenLoop.phase()` accepts `postponedAt: LocalDateTime?` and returns `POSTPONED` while the clock is before `postponedAt`; returns `RETURN` once `postponedAt` is reached, until the user clears or re-postpones.
- `FrictionPrefs` gains `openLoopPostponedAt: Flow<String?>` (ISO instant, `Instant.toString()`); `setOpenLoop(note, today, postponedAt)` writes the timestamp; `setOpenLoopPostponedAt(at)` updates just the timestamp without re-writing the note.
- `LauncherViewModel.openLoop` widens to a triple `(LoopPhase, String?, LocalDateTime?)`; the ViewModel wires the postponed-at flow into the phase.
- `HomeScreen.OpenLoopCard` gains a "Postpone" button on the RETURN state. A small time-picker dialog offers `Later today` / `Tomorrow morning` / `Pick a time`. The default is `Tomorrow morning` (the v0.25.0 fallback). A "Cancel postponement" affordance reverts to RETURN immediately.
- `OpenLoop.phase()` becomes a pure function — testable without a Context.

**Tests** (5 file-shape):
1. `LoopPhase.POSTPONED` is in the `LoopPhase` enum and is distinct from `CAPTURE` / `RETURN` / `NONE`.
2. `OpenLoop.phase()` returns `POSTPONED` when `note != null && postponedAt > now`.
3. `OpenLoop.phase()` returns `RETURN` when `postponedAt <= now && (notedDay == today || notedDay == today-1)`.
4. `OpenLoop.phase()` returns `NONE` when `note == null || postponedAt is null` (default fallback unchanged).
5. `OpenLoop.phase()` is timezone-stable: `postponedAt` is `Instant` (UTC); the comparison uses `Instant.now()` not local time.

## WP-B: DST-safe batch reschedule

**Why**: `ReportSchedule.nextRun` and the `armNext` call chain use `LocalDateTime.now() + ZoneId.systemDefault().toInstant()`. On a DST boundary, `setExactAndAllowWhileIdle` is given an *instant* — correct. But `nextRun` itself reads `LocalDateTime.now()` to compute the *next* target, which is wall-clock, not instant. Spring-forward (a 2am alarm scheduled on a day where 2am becomes 3am) can produce a target instant that's earlier than the current instant — which `setExactAndAllowWhileIdle` happily fires immediately, or never. We want the wall-clock semantics: "fire at 3am local time, whatever that means in UTC right now."

**Change**:
- `ReportSchedule.nextRun` returns `Instant` directly; the wall-clock-to-instant conversion happens inside `nextRun` with the timezone the caller passes in (the test surface uses a fixed `ZoneId.of("UTC")`).
- `armNext` re-derives the next target each call (already true), but the call site uses the *previous* decision (already true) — the bug is the wall-clock-instant conversion at boundary, not the arming loop.
- `ReportSchedule` is a pure function (already is), and gets a `nextInstantAt(now: Instant, zone: ZoneId, hour, minute, decision): Instant` overload that does the wall-clock math.
- Add a finding test that pins the spring-forward and fall-back behavior at a fixed instant.

**Tests** (5):
1. `nextInstantAt` returns an instant whose local hour/minute is `hour:minute` in the given zone.
2. On spring-forward day (e.g. 2026-03-29 in `America/New_York`), `nextInstantAt(now, ZoneId.of("America/New_York"), 2, 30)` returns an instant that maps to local 3:30 (because 2:30 doesn't exist).
3. On fall-back day (e.g. 2026-11-01 in `America/New_York`), `nextInstantAt(now, ZoneId.of("America/New_York"), 1, 30)` returns the *first* 1:30 (the second is ambiguous; we pick the post-transition instant — the rule is "fire at 1:30 wall-clock, prefer the later one so a DST-shift doesn't fire twice").
4. `nextInstantAt` is monotonic in `now` — if `now2 > now1`, the next firing after `now2` is not before the next firing after `now1`.
5. `ReportScheduler.armNext` does not call `LocalDateTime.now()` directly (the wall-clock calc moved to `ReportSchedule`).

## WP-C: "Did the report help?" one-tap feedback (Linardon 2024)

**Why**: Linardon's 2024 meta-analysis of digital self-help found one-tap "this helped / didn't help" ratings after a session predict retention better than the session content itself. The user doesn't need a survey — just two buttons. The data is local-only; no telemetry leaves the device.

**Change**:
- `ReportStore` gains `feedback: Flow<ReportFeedback?>` (nullable; cleared after read) and `recordFeedback(ReportFeedback)`.
- `ReportFeedback` is an enum: `HELPED`, `DIDNT_HELP`.
- `ReportScreen` shows a one-tap row at the bottom of the screen: 👍 "Helped" / 👎 "Didn't help". Tapping either records and hides the row. The row reappears when a new report is read.
- The feedback is shown in the *Settings → Last night's look* debug surface (local-only; pinned by finding test) so the user can see their own answers.

**Tests** (5):
1. `ReportFeedback` enum has exactly `HELPED` and `DIDNT_HELP`.
2. `ReportStore.recordFeedback(HELPED)` is reflected in `feedback.first()`.
3. `ReportStore.recordFeedback(HELPED)` followed by `recordFeedback(DIDNT_HELP)` is reflected as the latest.
4. `ReportScreen` has a "feedback row" composable that calls `recordFeedback(HELPED)` on 👍 tap and `recordFeedback(DIDNT_HELP)` on 👎 tap.
5. The feedback row is *only* present when there is a report to rate (i.e. inside the `else` branch of "no report yet").

## WP-D: Local-only PPG session telemetry

**Why**: A PPG session is a 30-60 second measurement. Right now the user has no record of when they measured and for how long — the value is stored, but the *act* of measuring is invisible. Local-only telemetry (start time, end time, duration) is a small addition that makes the action visible to the user in their own history.

**Change**:
- `PpgCapture` records `start: Instant` when the session begins, `end: Instant` when it finishes.
- `MeasuredStore` (or a new sibling) gains `ppgSessions: Flow<List<PpgSession>>` — append-only log of `PpgSession(start, end, durationSeconds, meanHr)`.
- A new "PPG history" line on `PpgScreen` shows the last 3 sessions (`Tue 8:14am · 45s · 72 bpm`).

**Tests** (5):
1. `PpgSession` data class has the 4 fields and `durationSeconds` is computed.
2. `MeasuredStore.appendPpgSession(PpgSession)` round-trips.
3. `PpgCapture` records `start` on session begin and `end` on session end (file-shape pin).
4. `PpgScreen` shows a "PPG history" composable that lists the last N sessions from `ppgSessions.first()`.
5. The history line is *only* present when `ppgSessions.first().isNotEmpty()`.

## WP-E: 14-day onboarding recap (Kanfer & Goldstein 1991)

**Why**: Kanfer & Goldstein's 1991 *self-regulation* review: a 14-day checkpoint is the earliest the user can detect a habit pattern (or its absence). The recap is opt-in (default off in Settings), and surfaces in the home corner next to the OpenLoop card.

**Change**:
- `Onboarding.kt` gains `installDay: LocalDate` and `recapSeenDay: LocalDate?` (the day the user last dismissed a recap).
- `OnboardingScreen.kt` gains a `RecapCard` composable that shows: "It's been 14 days. Here's what you did: N notes, M letters received, K PPG sessions, L night reports. Want a recap?" with a "Show me" / "Not now" pair.
- The recap is shown ONCE per 14-day window: between day 14 and day 21, then day 28-35, etc. After "Not now" or "Show me", the window closes.
- A finding test pins the window math (`daysSinceInstall in 14..20 inclusive → show`, `> 20 or < 14 → don't`).

**Tests** (5):
1. `Onboarding.installDay` is set on first launch and never changes.
2. `Onboarding.daysSinceInstall()` returns the integer days between `installDay` and `today`.
3. The recap is shown only when `daysSinceInstall in 14..20 || daysSinceInstall in 28..34 || ...` (window = 7 days starting at multiples of 14, offset 14).
4. The recap is suppressed if `recapSeenDay` is within the same window.
5. `OnboardingScreen` has a `RecapCard` composable that calls `markRecapSeen()` on "Not now" / "Show me".

## WP-F: "Today's one thing" micro-action card (Martell 2013)

**Why**: Martell's 2013 review of goal-setting: a single, narrow, today's-action card outperforms a list of goals on follow-through. The user picks ONE thing for the day; the card surfaces it on the home corner.

**Change**:
- `LauncherPrefs` gains `oneThing: Flow<String?>` and `setOneThing(text: String?)`. Default null.
- `HomeScreen` adds a `OneThingCard` composable that shows the user's chosen one thing for the day, with a "Done" button (clears it) and a "Change" button (text field).
- The card is silent when `oneThing` is null (default).

**Tests** (5):
1. `LauncherPrefs.oneThing` defaults to null.
2. `LauncherPrefs.setOneThing("Call mom")` then `oneThing.first()` returns `"Call mom"`.
3. `LauncherPrefs.setOneThing(null)` clears it.
4. `OneThingCard` is silent when `oneThing` is null.
5. `OneThingCard` has a "Done" button that calls `onDone()` (which calls `setOneThing(null)`).

## WP-G: Haptic-rich captures (Brewster CHI 2007)

**Why**: Brewster's CHI 2007 paper on rich tactile feedback: a single haptic for "save" is information-poor. Distinct feedback types (light tick for save, double-tap for delete, long buzz for "you've reached the end of the list") let the user navigate by feel. Right now only the QuickNotesCard Save button has a haptic (`HapticFeedbackType.LongPress`). The fix widens the surface.

**Change**:
- `LocalHapticFeedback` calls are added at 4 sites that currently have no feedback:
  - **NoteScreen row delete**: `HapticFeedbackType.LongPress` on tap.
  - **BedtimeList save**: `HapticFeedbackType.LongPress` on save.
  - **QuickNotesCard clear**: `HapticFeedbackType.TextHandleMove` (a soft "whoosh") on clear.
  - **LetterInbox delete**: `HapticFeedbackType.LongPress` on tap.
- A finding test pins the 4 import sites + the 4 call sites.
- The v0.25.1 `SaveHapticsFindingTest` is extended to assert that the *other* surfaces have *different* feedback types (i.e. a regression that copies the "save" haptic to all surfaces would fail the test).

**Tests** (5):
1. `NoteScreen` row delete has a `HapticFeedbackType.LongPress` call site.
2. `BedtimeList` save has a `HapticFeedbackType.LongPress` call site.
3. `QuickNotesCard` clear has a `HapticFeedbackType.TextHandleMove` call site.
4. `LetterInbox` delete has a `HapticFeedbackType.LongPress` call site.
5. `SaveHapticsFindingTest` (or a sibling) asserts that the 4 call sites are NOT all the same type — at least one is `TextHandleMove` (the clear case).

## WP-H: WorkManager offline retry for Drive backup

**Why**: v0.25.4's `BackupScheduler` makes a best-effort `append` on every note/letter write. If the device is offline, the call returns `NetworkError` and the entry is lost (the on-write trigger has no retry queue; the user has to tap "Back up now"). WorkManager with a `NetworkType.CONNECTED` constraint retries automatically.

**Change**:
- New `BackupRetryWorker` (CoroutineWorker) enqueues a one-time work request on every `NetworkError` from `BackupScheduler.append`. The work has a `NetworkType.CONNECTED` constraint and a backoff (10s, 30s, 2m, 5m — exponential).
- The worker reads the in-memory `pendingBackupQueue: List<PendingAppend>` and re-attempts the appends. On success, the queue item is removed; on `AuthExpired`, the worker fires a notification ("Sign in again to resume auto-backup") and abandons.
- The queue is persisted in `BackupPrefs` (DataStore) so the work survives process death.
- The `BackupScheduler.append` path gains a `try { ... } catch { enqueueRetry(...) }` wrapper that doesn't fail the user-visible save flow.

**Tests** (5):
1. `BackupRetryWorker` is a `CoroutineWorker` with a `NetworkType.CONNECTED` constraint (file-shape pin on the work request builder).
2. `BackupPrefs.pendingBackupQueue` is a `Flow<List<PendingAppend>>` and round-trips (Robolectric DataStore test).
3. `BackupScheduler.append` on `NetworkError` calls `enqueueRetry(PendingAppend(type, payload))` (finding test on the call site).
4. The retry queue is bounded at 100 entries (finding test on the trim path).
5. `BackupRetryWorker.doWork()` calls `target.append(...)` for each queued entry on success and removes the entry.
