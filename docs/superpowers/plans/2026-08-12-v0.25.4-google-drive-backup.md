# v0.25.4 — Google Drive backup (replaces WebDAV)

The user has decided to retire the v0.23.0 WebDAV bridge in favour of Google Drive as the project's cloud backup path. The local file picker (the "by the person, to a location they pick" path) stays untouched — it remains the default save destination, off by default, and is the third channel in a now three-way backup model.

The user's spec, captured 2026-08-12 14:22 IST in the v0.25.3 followup:

> "Backup in Google Drive the notes, journal etc as single document for each like whole journal though im giving in multiple it should be stored in google drive in one document file, whatever im adding new journal notes, it should automatically updated into that doc and sync in google drive."

Two design choices worth flagging up front (the user's directive was clear about both, but pinning them in the spec):

- **Per-type routing, not per-note.** One Drive file per content type (e.g., `MindAnchor-Notes.txt`, `MindAnchor-Letters.txt`). Multiple notes within a type append to the same file. The user said "one document for each" — `each` refers to the type, not each individual note.
- **Plain text format, not Google Docs API.** A text file in Drive is readable from any device, any text editor, the Drive web UI, and the Drive mobile app. It doesn't require the Docs API scope (smaller OAuth grant), doesn't have the formatting-quirks of a programmatically-built Google Doc, and is the smallest possible dependency surface.

## Design notes

### Why raw REST, not `play-services-drive`

The Google API client for Android (`play-services-drive`) is a 1.2 MB AAR that wraps the Drive REST API. The Drive REST API is JSON over HTTPS with `Authorization: Bearer <access_token>`. Calling the same endpoints with OkHttp is ~50 lines of code (one `OkHttpClient`, one `Request`, one `Response` handler) and adds zero AAR. The OAuth token comes from `play-services-auth` (0.4 MB, we already pull the rest of the project through `play-services-*` via Health Connect's transitive deps), so we already pay the play-services tax — adding a Drive AAR on top of that is dead weight for an API that fits in 50 lines of OkHttp.

### Why one file per content type, not per note

The user's spec is explicit: "single document for each like whole journal though im giving in multiple it should be stored in google drive in one document file". `Each` = each content type, not each individual entry. The append-only model is also the simplest to reason about: the file is a long, growing log; reads are full-file (or byte-range); writes are append. The Drive REST API's `?uploadType=multipart` + a `Content-Range: bytes */N` header does append in two round-trips (one to discover the current size, one to PUT the new range) — or, with a cached size from a recent read, in one round-trip.

For v0.25.4, the two content types are:
- `Notes` — the home-screen quick-capture (and any future freeform-text journal — see WP-D below)
- `Letters` — the v0.25.2 daily letter

Each gets one file:
- `MindAnchor-Notes.txt`
- `MindAnchor-Letters.txt`

Future content types (CheckIn entries, reading data, etc.) get added to the enum and a new file as they're backed up.

### What about format inside the file?

Each line in the file is a JSON object (one `BackupCodec.Backup` minus the `note` field — just the date + the body). The file is the JSON-Lines format (`\n`-delimited JSON, one entry per line). Reading the file is `for line in file.split("\n"): decode(line)`. Writing the file is `append(format_date(body))`. This is the simplest possible format that:
- Survives Drive's web UI "open in Google Docs" conversion (it'll be a one-line-per-entry list — readable)
- Survives a manual download (you get a `.txt` file you can grep)
- Doesn't require a Docs API scope

A small migration: the existing v0.25.2 BackupCodec format (one big JSON object, all entries) is the on-the-wire format. The per-type file format is a different shape (one entry per line). The conversion is `BackupCodec.encode(list).let { it.lines().joinToString("\n") }` — a few lines of glue.

### OAuth flow

`play-services-auth` gives us `GoogleSignIn.getSignedInAccountFromIntent(...)` and a `GoogleSignInClient.silentSignIn()` for the cached account. The Drive scope we need is `https://www.googleapis.com/auth/drive.file` (the narrowest "per-file access" scope, NOT the full Drive scope — important for user trust, since `drive.file` only sees files the app created). The token comes back as a `GoogleAccountCredential` from the auth library, and OkHttp just adds `Authorization: Bearer ${token}` to every request.

The sign-in flow:
1. User opens Settings → Drive backup
2. "Sign in with Google" button → `GoogleSignIn.getClient(this, GoogleSignInOptions.DEFAULT_SIGN_IN.withDriveScopes())`
3. User picks an account, grants the `drive.file` scope
4. App receives the `GoogleSignInAccount`, extracts the email + ID token, stores the email in DataStore for UI display, fetches a server auth code, exchanges it for a refresh + access token, stores the refresh token in EncryptedSharedPreferences
5. Subsequent calls use the access token; the silent-sign-in path refreshes it before expiry

The refresh token is the long-lived secret; the access token is short-lived (1 hour). The refresh lives in EncryptedSharedPreferences, the access token is recomputed on every operation from the refresh.

### Sync trigger

For the first iteration, sync is **on-write** (every new note / letter triggers an append). The simple MVP: the existing `BackupScheduler` (or a new `DriveBackupScheduler`) hooks into the `NoteStore` and `LetterStore` save events via their `Flow`s; on each new entry, it appends to the right Drive file. The v0.23.0 WebDAV bridge did "Back up now" full-file uploads — Drive's per-type append model is incremental and faster.

If the user is offline, the append is queued in DataStore (the same `letters_read_dates` key pattern from v0.25.3-WP-C) and retried on next online. The retry uses the existing `WorkManager` worker pattern.
