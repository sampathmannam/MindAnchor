## WP-H: BackupRetryWorker — drain the pending queue

**Why**: v0.25.5's data layer enqueues a `PendingBackup` whenever the on-write trigger's `BackupTarget.append` returns non-`Ok`. But nothing drains the queue. A user whose phone is offline overnight accumulates entries; the entries sit in DataStore until the user manually taps "Back up now" or until they age out of the `MAX_PENDING = 100` trim. The whole point of v0.25.5-WP-H was to *stop* the silent-failure mode; without the worker, the silent-failure mode is alive and well — just at one indirection further.

**Change**:
- New `BackupRetryWorker : CoroutineWorker(appContext, params)` in `app/src/main/java/org/mindanchor/backup/`.
- `doWork()` reads the pending queue, picks the right `BackupTarget` for each entry's `ContentType`, and calls `target.append(type, payload)`:
  - `ContentType.Notes` → the same target the `BackupScheduler` is wired to (the call site passes the targets at enqueue time via a small `BackupTargets` data class — see "wiring" below).
  - `ContentType.Letters` → the same.
- On `AppendResult.Ok` → `removePending(entry)`, continue with the next.
- On any non-`Ok` result → stop draining, return `Result.retry()` so WorkManager backs off and tries again on the next `CONNECTED` tick.
- `enqueueIfNeeded(context)` static method: `OneTimeWorkRequestBuilder<BackupRetryWorker>().setConstraints(NetworkType.CONNECTED).build()` + `WorkManager.getInstance(context).enqueueUniqueWork(NAME, ExistingWorkPolicy.KEEP, request)`. `KEEP` not `REPLACE` — a worker already running will not be cancelled by a second enqueue, and the second enqueue is a no-op (WorkManager's `KEEP` policy).
- `BackupScheduler.encryptAndAppend` calls `BackupRetryWorker.enqueueIfNeeded(context)` after every successful `enqueuePending`, so the work is scheduled as soon as the queue is touched.
- The worker uses `applicationContext` and a freshly-built `BackupPrefs` + `BackupRepository` (the v0.25.4 OAuth bridge) — the same pattern `BackupScheduler` uses. No Hilt, no DI graph; the class is instantiable by WorkManager's default factory.

### Wiring the targets

The on-write trigger holds the `notesTarget` and `lettersTarget` as constructor parameters. The worker, scheduled from inside the on-write path, can read them via the same `BackupRepository` the scheduler uses. The simplest design: `BackupRepository.targetFor(type: ContentType): BackupTarget` is the existing lookup; the worker calls it per entry. No new class needed.

### Failure mode

- A `PendingBackup` whose target returns `NetworkError` mid-drain → worker returns `Result.retry()`; the failed entry stays in the queue; the rest of the queue is left for the next run.
- A `PendingBackup` whose target returns `AuthExpired` → same: retry until the user re-signs in. A future improvement could surface a notification, but the current scope is "drain the queue" — the user-visible signal is the same as it was (the Settings sub-section's "Sign in with Google" button is the bridge).
- A `PendingBackup` whose payload is corrupt on disk (decoded but the bytes don't match the expected length, etc.) → `PendingBackupLog.decode` already drops corrupt lines, so the worker only sees well-formed entries. Defense in depth: the worker's `runCatching` wrapper around the per-entry append is also fail-soft.

**Tests** (5 file-shape):
1. `BackupRetryWorker` extends `CoroutineWorker` and the class file is under `app/src/main/java/org/mindanchor/backup/`.
2. `BackupRetryWorker.enqueueIfNeeded` builds a `OneTimeWorkRequest` with `setRequiredNetworkType(CONNECTED)` (file-shape pin on the request builder).
3. `BackupRetryWorker.doWork` reads the pending queue from `BackupPrefs`, dispatches per `ContentType` to the right `BackupTarget`, and removes the entry on `AppendResult.Ok`.
4. `BackupRetryWorker.doWork` returns `Result.retry()` when any entry returns a non-`Ok` `AppendResult`, and leaves the failed entry in the queue.
5. `BackupScheduler.encryptAndAppend` calls `BackupRetryWorker.enqueueIfNeeded(context)` after every successful `backupPrefs.enqueuePending` call (file-shape pin on the call site).

## Out of scope (deferred)

- **Two-provider option (Drive + WebDAV)** — needs `BackupTarget` interface to grow a provider-chooser. A future v0.25.6+ surface; not v0.25.6.
- **Google Docs format** — needs the Docs API scope and a different wire format. A future v0.25.6+ surface.
- **Auto-sync for night report / EMA / PPG** — needs `BackupEntry`-shaped data for each. The v0.25.5-WP-H enqueue path is already type-agnostic (`PendingBackup` carries `ContentType`), so the worker can be extended to drain additional content types in a follow-up.
- **`BackupRetryWorker` AuthExpired notification** — the user can already see the "Sign in with Google" button in the Settings sub-section; the failure mode is visible. A future "post a heads-up notification" is a v0.25.6+ candidate.
- **Watch-connect real root-cause fix (v0.25.3-WP-B-real)** — still needs the user's `adb logcat -s MindAnchor/HealthConnect:V` capture.
- **Manual smoke** — still AVD-unavailable on this Windows host; all surfaces are pinned by 5+ finding tests each.
